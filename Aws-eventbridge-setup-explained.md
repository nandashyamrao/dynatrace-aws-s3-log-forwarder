# 🔁 End-to-End Explanation: InfoSec to EMS S3 Event Forwarding via EventBridge

This document provides a clear explanation of how S3 object creation events from InfoSec-owned buckets are automatically forwarded to EMS accounts, where logs are processed and sent to Dynatrace.

---

## 🧩 Goal

To create an **automated, secure, scalable pipeline** that allows CloudTrail, WAF, and CloudFront log events stored in InfoSec-owned S3 buckets to be **forwarded to EMS environments**, where they can be processed by a Lambda forwarder and ingested into **Dynatrace**.

---

## 🛠️ How the Setup Works (Step-by-Step)

### 1. **S3 Buckets (Owned by InfoSec)**
- InfoSec owns and manages four key S3 buckets:
  - `sf-prod-event-trail`
  - `sf-test-event-trail`
  - `aws-waf-logs-sf-mgmt-prod-us-east-1`
  - `sf-infosec-cloudfront-logs`
- These buckets store log files generated by CloudTrail, WAFv2, and CloudFront.

---

### 2. **Enable S3 → EventBridge Integration**
- On each bucket, the **“Send events to Amazon EventBridge”** option is enabled.
- This automatically sends **all `ObjectCreated` events** to the InfoSec account’s **default EventBridge** service.

---

### 3. **EventBridge Rules in InfoSec Account**
- EventBridge rules are created to **filter only relevant buckets** and **`ObjectCreated` events**.
- Each rule targets the **default EventBridge bus** in the appropriate EMS account:
  - Prod logs go to `sf-ems-prod` (account `125232492988`)
  - Test logs go to `sf-ems-test` (account `351454108853`)

---

### 4. **Cross-Account Targeting**
- The rules use `aws_cloudwatch_event_target` to forward events to:
  - `arn:aws:events:us-east-1:125232492988:event-bus/default` (for prod)
  - `arn:aws:events:us-east-1:351454108853:event-bus/default` (for test)
- An IAM role with `events:PutEvents` permission is attached to allow this.

---

### 5. **Permissions in EMS Accounts**
- Each EMS account allows the InfoSec account (`808693921418`) to **PutEvents** into their default event bus using:
  ```hcl
  resource "aws_cloudwatch_event_permission" { ... }
  ```

---

### 6. **EMS-Side EventBridge Rule**
- In EMS, a local rule picks up these events from its own default bus.
- The rule **targets an SQS queue** (or directly a Lambda) for processing.

---

### 7. **Lambda: S3 Log Forwarder**
- A Lambda function reads from the SQS queue.
- It:
  - Downloads the object from S3
  - Decompresses it (if `.gz`)
  - Parses individual log events
  - Sends them to **Dynatrace’s Log Ingest API**

---

## ✅ Why This Works Well

| Feature                     | Benefit                                                      |
|-----------------------------|--------------------------------------------------------------|
| 🔄 EventBridge Integration  | Serverless, scalable, no need for direct SQS/SNS hooks       |
| 🔐 Cross-account Security   | IAM-controlled access ensures tight permissions              |
| ⚙️ Decoupled Architecture   | Producers and consumers are isolated for flexibility         |
| 🧠 Observability            | Dynatrace receives structured logs for monitoring & alerting |

---

## 📬 Summary

This setup enables InfoSec to retain ownership of log data while securely and automatically forwarding it to EMS environments for observability. Using **EventBridge and cross-account IAM**, it’s flexible, scalable, and compliant with enterprise standards.
