🧱 Step 1: Setup (One-time)

*   **Dynatrace Team** configures these credentials securely (Parameter Store / Secrets Manager).

* * *

🔑 Step 2: Authentication Request (Initial Login)
-------------------------------------------------

1.  **Dynatrace Extension** sends a request to the Salesforce **OAuth 2.0 token endpoint**:
    ```
    https://login.salesforce.com/services/oauth2/token
    ```
    or sandbox:
    ```
    https://test.salesforce.com/services/oauth2/token
    ```
    Request contains:
    *   `grant_type` (e.g., `password` or `client_credentials` or `refresh_token`)
    *   `client_id` (Consumer Key)
    *   `client_secret` (Consumer Secret)
    *   `username` + `password` of integration user (if using password flow)
    *   or signed JWT (if using server-to-server JWT flow)

* * *

🔄 Step 3: Salesforce Validation
--------------------------------

*   Salesforce validates the **Connected App configuration** (is the app approved, scopes allowed, correct keys).
*   Validates **integration user** permissions (does this user have API access and is the app assigned to them).

If valid → Salesforce issues tokens:

*   **Access Token** (short-lived, usually valid for minutes to an hour).
*   **Refresh Token** (long-lived, used to get new access tokens without user re-login).

* * *

📡 Step 4: Data Access
----------------------

*   Dynatrace uses the **Access Token** in the `Authorization: Bearer <token>` header for Salesforce API calls.
*   Example API endpoint:
    ```
    GET https://<instance>.salesforce.com/services/data/vXX.X/sobjects/Account/
    ```
*   Salesforce responds with requested data (metrics, objects, events, logs).

* * *

🔁 Step 5: Token Refresh
------------------------

*   When the Access Token expires, Dynatrace uses the **Refresh Token** to request a new Access Token.
*   This avoids downtime or re-login.
*   Salesforce issues a new Access Token as long as the refresh token is valid.

* * *

🚨 Step 6: Error Handling
-------------------------

*   If **Refresh Token expires or is revoked** → Dynatrace loses access.
*   Admin must re-authorize the Connected App or reissue tokens.
*   Common failure points:
    *   Wrong scopes (API not enabled).
    *   Integration user doesn’t have data permissions.
    *   Consumer Key/Secret mismatch.
    *   IP restrictions in Salesforce policies.

* * *

* * *

🔑 Principle Behind OAuth, Client Secret, Consumer Key & Integration User
=========================================================================

1\. Why OAuth at All?
---------------------

*   In the **old days**, external systems (like Dynatrace) would log into Salesforce using **username + password** of a user.
*   That’s insecure because:
    *   Passwords can be stolen.
    *   If the user changes password, integration breaks.
    *   Hard to restrict what the integration can/can’t do.

👉 Enter **OAuth 2.0** — an open standard that lets **applications** (like Dynatrace) securely access Salesforce APIs without needing to know a user’s raw password.

* * *

2\. Connected App = Doorway Into Salesforce
-------------------------------------------

*   In Salesforce, you don’t just let any app in.
*   You create a **Connected App** = a secure “doorway” through which external systems connect.
*   When you create this app, Salesforce generates two key credentials:

### 🔑 Consumer Key (Client ID)

*   Public identifier of the app.
*   Think of it like a **username for the app itself** (not a person).

### 🔒 Consumer Secret (Client Secret)

*   Private credential of the app.
*   Think of it like a **password for the app itself**.
*   Must be stored securely (Dynatrace uses AWS SSM Parameter Store / Vault).

Together, these prove:  
👉 “This request is coming from the Dynatrace extension app, not some random hacker.”

* * *

3\. Integration User (Service Account)
--------------------------------------

*   Apps also need a **user identity** inside Salesforce to know _whose data to access_.
*   That’s where the **integration user** comes in:
    *   A dedicated service account in Salesforce (not tied to a real employee).
    *   Has the exact permissions needed (API access, object read, etc.).
    *   Is assigned to the Connected App through profiles or permission sets.

👉 So Dynatrace connects as **itself (the app)** _and_ on behalf of **the integration user**.

* * *

4\. How It All Works (Under the Hood)
-------------------------------------

### Step A – Dynatrace Sends Auth Request

Dynatrace → Salesforce OAuth endpoint (`/services/oauth2/token`) with:

*   `client_id` (Consumer Key)
*   `client_secret` (Consumer Secret)
*   Integration user credentials (username+password) **OR** JWT signed by Dynatrace if using server-to-server flow.

### Step B – Salesforce Validates

Salesforce checks:

*   Is this a valid Connected App (Consumer Key + Secret match)?
*   Is this user allowed to use the app (integration user + assigned scopes)?

### Step C – Token Issued

If valid, Salesforce issues:

*   **Access Token** (short-lived passport to make API calls).
*   **Refresh Token** (longer-lived, can request new access tokens).

### Step D – Dynatrace Uses Token

*   Every API call to Salesforce includes:
    ```
    Authorization: Bearer <access_token>
    ```
*   Salesforce knows this request is from Dynatrace, acting on behalf of the integration user.

* * *

5\. JWT vs Username+Password Flow
---------------------------------

*   **Password Flow**: Dynatrace uses integration user’s username+password + client\_id/secret to get tokens.
    *   Easier to set up, but less secure.
*   **JWT Flow**: Dynatrace uses a signed certificate (JWT assertion) + client\_id to request tokens.
    *   More secure, no password stored, often preferred in enterprise setups.

* * *

📌 Why Both Are Needed (Summary)
--------------------------------

*   **Consumer Key + Secret** → prove _which application_ is connecting (Dynatrace extension).
*   **Integration User** → prove _on whose behalf_ the app is acting inside Salesforce.

Together, they allow **secure, controlled, and auditable access** to Salesforce APIs for monitoring in Dynatrace.

Let me break it down.

* * *

🔐 What Secures OAuth vs Plain Username/Password
================================================

1\. 🔑 App Identity (Consumer Key + Secret)
-------------------------------------------

*   In plain logins, anyone with username/password could connect.
*   With OAuth, **two layers** are required:
    *   App’s identity (Consumer Key + Secret)
    *   User’s identity (Integration user credentials OR JWT)
*   This makes it **much harder to impersonate**, because an attacker would need _both_ sets of credentials.

* * *

2\. 🎟️ Tokens Instead of Passwords
-----------------------------------

*   Dynatrace never sends the user’s password on every request.
*   It sends a **short-lived Access Token**.
*   Tokens expire quickly (minutes–hours). If stolen, they become useless.
*   With old username+password auth, a stolen password = unlimited access until changed.

* * *

3\. 🔄 Refresh Tokens & Revocation
----------------------------------

*   Salesforce can issue a **Refresh Token** that allows Dynatrace to request new Access Tokens.
*   If compromised, an admin can **revoke the token** in Salesforce — instantly cutting off access.
*   With just a password login, revocation meant disabling the user or changing their password (messy).

* * *

4\. 🔒 Scoped Permissions
-------------------------

*   OAuth scopes define exactly what the app can do (e.g., `api`, `read_only`).
*   Even if Dynatrace has a valid token, it **cannot exceed those scopes**.
*   In old username+password auth, if the user had broad permissions, the integration got full access.

* * *

5\. ✅ Safer Alternatives to Username/Password
---------------------------------------------

Salesforce strongly recommends avoiding the **password flow** where possible. Two stronger options:

*   **JWT Bearer Flow**
    *   Uses a **signed certificate** instead of a password.
    *   Dynatrace signs a JWT with its private key → Salesforce verifies with the public key.
    *   No password stored anywhere.
*   **Authorization Code Flow (3-legged)**
    *   Typically used for user logins, not service integrations.

👉 For your POC, Salesforce team might start with password flow (simpler), but in enterprise rollout you’d push for **JWT flow** because it eliminates username/password storage entirely.

* * *

📌 Bottom Line
--------------

*   Yes, in the **password flow** there’s still a username+password, but it’s wrapped in OAuth:
    *   Used only once to get tokens.
    *   Tokens are short-lived, scoped, and revocable.
    *   Consumer Key/Secret ensures the request really comes from Dynatrace.
*   In **best practice setups (JWT)** → no password at all, only app certificates + tokens.

Let me put it clearly: in **Salesforce OAuth flows that still use a password** (like the “username+password” flow), that password is **not used alone** — it’s **blended** with the **Connected App’s identity**.

* * *

🔐 How the Security Layers Blend Together
=========================================

### 1\. **Old World (Just Password)**

*   External system says: “Here’s my username + password.”
*   If valid, Salesforce says: “Cool, full access!”
*   Problem: Anyone who steals that password can impersonate the user forever.

* * *

### 2\. **OAuth Password Flow (Blended Identity)**

When Dynatrace connects, it sends:

*   **User Identity** → Integration user’s username + password.
*   **App Identity** → Consumer Key + Consumer Secret from the Connected App.

Salesforce checks:

1.  ✅ Is this the right **app** (Connected App ID + secret)?
2.  ✅ Is this the right **user** (integration account)?
3.  ✅ Does this app have permission to act on behalf of this user?
4.  ✅ Are the requested scopes allowed (e.g., `api`, `refresh_token`)?

👉 Only if all four are true does Salesforce issue an **Access Token**.

2\. Why JWT Instead of Password?
--------------------------------

*   With password flow, Dynatrace must store a Salesforce username + password = risk.
*   With JWT flow:
    *   No password stored.
    *   Instead, a **certificate pair (public/private)** is used.
    *   Private key stays with Dynatrace → never leaves your control.
    *   Public key is uploaded into Salesforce Connected App.

3\. How JWT Assertion Works (Step by Step)
------------------------------------------

### Step A – Dynatrace Prepares JWT

Dynatrace builds a signed JWT (JSON object) with these claims:

*   **iss** → issuer = Consumer Key (Connected App ID)
*   **sub** → subject = Salesforce integration user (e.g., `integrationuser@company.com`)
*   **aud** → audience = Salesforce login endpoint (`https://login.salesforce.com` or sandbox URL)
*   **exp** → expiration time (short, e.g., 3–5 minutes from now)

Example (before signing):

```json
{
  "iss": "3MVG9rFJvQRVOvk5H5...", 
  "sub": "integrationuser@company.com",
  "aud": "https://login.salesforce.com",
  "exp": 1738527600
}
```

Dynatrace then **signs this JWT** with its **private key** → result = `JWT assertion`.

* * *

### Step B – Dynatrace Sends Token Request

Dynatrace makes a call to Salesforce OAuth endpoint:

```
POST https://login.salesforce.com/services/oauth2/token
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer
assertion=<signed_JWT_assertion>
```

* * *

### Step C – Salesforce Validates

1.  Verifies the JWT signature using the **public key** from the Connected App.
2.  Checks that the Connected App + Integration User are authorized.
3.  Confirms `aud` (audience) matches Salesforce domain.
4.  Confirms `exp` hasn’t expired.

* * *

### Step D – Salesforce Issues Tokens

If valid → Salesforce responds with:

*   **Access Token** (short-lived, used in API calls)
*   (Optional) **Refresh Token** if configured

* * *

### Step E – Dynatrace Uses Access Token

*   Dynatrace calls Salesforce APIs with:
    ```
    Authorization: Bearer <access_token>
    ```
*   When Access Token expires, Dynatrace just **repeats the JWT assertion** process (no password needed).
